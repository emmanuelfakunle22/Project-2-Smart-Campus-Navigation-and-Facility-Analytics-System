CSCE 2110 Project 2 - Design Document (Final)
=============================================

1. Hash function
----------------
Key: the facility ID after trimming and converting to uppercase (e.g. "F004").
Formula (polynomial rolling hash, base 31):

    h = 0
    for each character c in key:
        h = (h * 31 + ASCII(c)) mod capacity
    index = h

Taking mod capacity at every step keeps h small, so it never overflows.
Because the key is uppercased first, "f004" and "F004" always produce the
same index. std::hash is not used.

2. Collision strategy: separate chaining
----------------------------------------
Each bucket is a chain (std::vector<Facility>). A new entry is appended to
the chain at its index. We chose chaining because:
  - chains grow, so there is no fixed maximum number of facilities (HASH-5);
  - the table can never become "full", so no full-table rejection is needed;
  - insert, lookup, and duplicate detection are simple: scan one short chain.
Lookup only searches the single bucket the key hashes to; it never scans all
facilities. Duplicate keys: insert() scans the chain first; if the ID exists
it returns false, the original entry is unchanged, and no collision is counted.

3. Collision counting
---------------------
A collision = one accepted insertion into a bucket that already holds at
least one entry. Rejected records (including duplicate IDs) never add to the
count. Example (testdata/collision, capacity 11): F001, F013, F025 all hash
to bucket 3, so F013 and F025 each count once -> collisions 2. The duplicate
f013 is rejected and the count stays 2.

4. Capacity and full-table behavior
-----------------------------------
Initial capacity: 11 buckets (prime), set by DEFAULT_HASH_CAPACITY in
HashTable.h (also a constructor parameter). With chaining the table never
fills; any number of facilities can be stored. Resizing is not implemented.

5. Facility name and category search, category report
-----------------------------------------------------
Name and category searches are a straightforward scan of the file-order
facility vector, comparing lowercase trimmed strings (whole value only, so
internal spaces must match). Every match prints in file order with a count.
The category report builds two parallel vectors in first-seen order:
distinct category spellings (first accepted spelling kept) and their counts,
grouping by lowercase comparison. Percentage = count * 100 / total, printed
to one decimal place. With no facilities, the report prints a message and
total 0 before any division happens.

6. Graph representation: adjacency list
---------------------------------------
CampusGraph stores:
  - names: vector<string>, vertex i = i-th accepted building (file order);
  - adj:   vector<vector<int>>, adj[i] = neighbor indices in insertion order;
  - edgeCount: each undirected edge counted once.
Adding edge A-B appends B to adj[A] and A to adj[B] and increments edgeCount
once. Duplicate and reversed connections are caught by checking whether B is
already in adj[A]. We chose an adjacency list because the campus graph is
sparse, it grows naturally, degree = adj[i].size(), and neighbor insertion
order (which determines BFS order) is kept automatically. Neighbors are never
sorted. The same graph object is used for every graph feature.

7. BFS reachability and shortest path
-------------------------------------
Reachability: std::queue<int>, vector<bool> visited, vector<int> dist. A
building is marked visited when it is enqueued, and
dist[next] = dist[current] + 1.
Shortest path: the same BFS, but it records parent[next] = current when a
building is first discovered, and stops once the destination is visited.
The path is rebuilt by following parent links back from the destination,
then printed in forward order; connections = path length - 1. Because
neighbors are scanned in insertion order and a parent is set only the first
time a building is seen, ties go to the route through the earlier neighbor
(Library -> Student Union -> Gym). Same start and destination prints that
building and 0; an unvisited destination means no path.

8. Department tree
------------------
General tree: DepartmentNode {name, parent pointer, vector<DepartmentNode*>
children}, children in insertion order. Search is a recursive depth-first
scan (case-insensitive). Depth = number of parent links to the root.
  - Hierarchy and preorder: recursive, node then each child.
  - Postorder: recursive, each child then the node.
  - Level-order: std::queue of node pointers; dequeue, print, enqueue
    children left to right.
  - Statistics: one recursive pass counting nodes, leaves (no children), and
    the maximum depth (= height). An empty tree prints 0, 0, N/A; a root-only
    tree is 1, 1, 0.
The destructor frees every node with a postorder delete (Valgrind clean).

9. Connectivity report
----------------------
Uses the shared adjacency list. Highest degree is the largest adj[i].size();
every building with that degree is listed (ties included). Isolated buildings
have degree 0 (or "None"). Components: loop over all buildings, and each
time an unvisited building is found, run a BFS that marks its whole
component and add one to the count. An isolated building is its own
component. No buildings prints zero totals and 0 components.

10. Main classes / modules
--------------------------
Utils            trim, case conversion, '|' splitting, comment check, warnings
Facility         struct: id, name, building, category
HashTable        custom separate-chaining table keyed by facility ID
FacilityDatabase loads facilities.txt; file-order list + HashTable; ID, name
                 and category search; category report
CampusGraph      loads buildings/connections; display, counts/degrees, BFS,
                 shortest path, connectivity report
DepartmentTree   loads departments.txt; add, search, hierarchy, preorder,
                 postorder, level-order, statistics
main.cpp         reads the data-directory argument, loads files, runs the menu
